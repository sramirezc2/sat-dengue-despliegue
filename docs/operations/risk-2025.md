## Autoridad y significado

Base: `a9c2c1abac386053b2e78f072bdb44e0141f4045`. Única receta:
`pipeline/conf/retroanalisis/noche/log_conclima.yml`, SHA-256

No intervienen EXP004/EXP006, búsqueda, calibración, umbrales o promoción de champion.
El modelo es logística L2, scikit-learn 1.7.2, semilla 53, C=1, 5000 iteraciones.
Las 33 entradas ordenadas, 36 columnas de matriz, log1p, one-hot y escalado son
exactamente los declarados por la receta; el artefacto incorpora sus listas completas.

Se ajusta un modelo global Meta–Tolima con objetivos 2012-01 a 2024-09 y demora
de etiqueta de un mes: disponibilidad máxima 2024-10, anterior al primer origen
2024-11. Se construyen etiquetas únicamente durante materialización, sobre ese
prefijo anterior a 2025. No se transportan al scoring ni al paquete público.
La vista separada permite observaciones hasta T, incluyendo conteos y estado
actual de 2025 cuando T pertenece a 2025. No admite estados posteriores a T.
Los guards del canónico de desarrollo continúan excluyendo 2025.

Es inferencia retrospectiva con datos consolidados; las fechas de evento no
prueban disponibilidad histórica de esas versiones en tiempo real. No es
holdout intacto ni reproducción exacta del retroanálisis que reajustaba cada mes.
Se publica únicamente T+2: enero de 2025 usa noviembre de 2024 y diciembre de
2025 usa octubre de 2025. No se generan objetivos de 2026. T+1 queda deshabilitado

Los 76 municipios permanecen en cada documento. Son elegibles aquellos con
estado en T conocido, sin exceso y con predictores completos. El ranking ordena
solo elegibles, por margen lineal descendente y DIVIPOLA ascendente en empates.

## Grafo y entradas

`risk_2025_publication` registra seis nodos secuenciales:

| Etapa | Implementación | Entrada → salida / compuerta |
|---|---|---|
| Identidad | `risk/nodes.py:preflight` | receta, parámetros, artefacto/certificado → contexto; pins incompatibles detienen antes de adquirir |
| Cinco fuentes | `risk/nodes.py:sources`, adquisición existente | manifiesto crudo aprobado → `ResolvedBundle`; hashes/tamaños/cache local verificados |
| Congelación | `risk/frozen.py`, productores existentes | prefijo hasta 2024-10 → estado canónico; exactamente un fit, ninguna observación posterior |
| Scoring mensual | `risk/inference.py`, `raw/panel.py:source_panel` | claves temporales → prefijo hasta T → predictores → margen interno → ranking/cupo; cero etiquetas |
| Paquete | `risk/publication.py` | doce documentos → manifiesto canónico; contrato, calendario, linaje y hashes comunes |
| Promoción | publicador transaccional existente | staging validado → edición inmutable; rollback ante fallo |

`catalog_risk_2025.yml` declara `risk_context` en memoria con `copy_mode=assign`,
para conservar etapas y hashes del recibo entre nodos del runner secuencial.
Los demás resultados intermedios son datasets de memoria; no hay CSV manuales.
La proyección temporal interpreta primero claves de fecha/municipio y recorta
antes de normalizar valores. No importa constructores de desenlaces.

La fuente aprobada es el manifiesto crudo operacional existente de cinco archivos.
El cache se resuelve exclusivamente bajo `pipeline/data/01_raw/inbox/` de este
worktree. Si está ausente, la adquisición existente se ejecuta dentro del mismo
grafo; necesita el acceso privado previamente configurado. Nunca se escribe el
token ni se publica una ruta privada. La adquisición solo se ejecuta después de todos los gates de software.

## Dos modos y comando único

Todos los comandos siguientes se ejecutan desde la raíz de ESTE worktree.
No ejecutar materialización, certificación ni E2E intensivo mientras EXP006 siga activo.

1. **Materialización autorizada:** `risk_2025.mode=materialize`. Ajusta una vez por
   ejecución, guarda modelo y manifiesto en un directorio nuevo, calcula el lote
   completo para certificar su hash y termina `MATERIALIZED_NOT_PUBLISHED`.
   Nunca promueve. Ejemplo de una ejecución, cuando se autorice:

   ```sh
   uv run --locked --directory pipeline kedro run --pipeline risk_2025_publication --params 'risk_2025.mode=materialize,risk_2025.artifact_directory=data/risk-2025/materialization-001'
   ```

2. **Publicación ordinaria:** `risk_2025.mode=frozen`, predeterminado. Exige modelo,
   manifiesto, SHA del modelo y certificado N=3 aprobado por su SHA. No llama fit,
   ni entrena como fallback. La configuración sin identidad activada falla cerrada.

Después del gate de EXP006 y las verificaciones completas, el certificador lanza
tres procesos Kedro aislados con artefactos y recibos propios, sin promover. Solo
si los tres hashes de modelo y paquete coinciden puede registrar los pins locales:

```sh
uv run --locked --directory pipeline python tools/certify_risk_2025.py --activate
```

El resultado queda en `pipeline/data/risk-2025/certifications/<id>/`; `approved.json`
en ese mismo espacio de datos registra las cuatro identidades/rutas relativas
necesarias. No se sobreescribe una activación diferente. No hay transferencia
manual de predictores, modelo o resultados entre comandos. Una certificación
`--synthetic` nunca puede activar la publicación científica.

Con el artefacto certificado y activado, el recorrido completo ordinario es:

```sh
uv run --locked --directory pipeline kedro run --pipeline risk_2025_publication
```

También se pueden fijar los cuatro pins explícitos mediante parámetros Kedro:
`artifact_directory`, `artifact_sha256`, `certificate`, `certificate_sha256`.
Un artefacto de código, lock, receta, esquema o datos distintos es rechazado.
La edición predeterminada es `2025-log-climate-v1`. La identidad de código incluye
HEAD y digest de fuentes Python/JSON del subproyecto, no tiempos ni rutas.
Antes de certificar, cerrar cambios de código científico. Un descendiente documental
se acepta solo si código científico/JSON, lock y manifiesto crudo siguen idénticos;
el artefacto y la publicación conservan el SHA original del ajuste. No repetir N=3 real sin una razón y autorización aplicables.

El modelo utiliza la representación JSON canónica del adaptador, con floats
completos para coeficientes, intercepto, medias y desviaciones. Incluye parámetros
nativos, versión, dtypes/orden, receta, corte, digest de claves/X/y de aprendizaje
y estado efectivo. No altera el `model_json` redondeado usado en evidencia antigua.
La fecha lógica fija `2024-11-01T00:00:00Z` es un ancla de certificación, no afirma
que se produjo el artefacto en esa fecha. Los recibos de cada intento son operacionales.

## Fallos y recuperación

Los recibos están en `pipeline/data/risk-2025/runs/<id>/receipt.json`, con etapa,
estado y tipo de error sanitizado; no en evidencia cerrada. No reutilizar IDs,
eliminar locks, corregir evidencia ni borrar un intento fallido. Receta, hash,
biblioteca, esquema, cobertura o cupo incompatibles detienen el lote completo.
El paquete ordinario también debe coincidir con el hash certificado.

Staging y manifiesto se revalidan antes de promover. El publicador usa su lock,
respaldos, reemplazos atómicos por archivo y rollback existentes. Una edición
nueva no se configura en la API hasta terminar COMMITTED: no se afirma atomicidad
de un directorio completo para lectores concurrentes. Durante una entrega parcial
la API rechaza el lote. Ante rollback incompleto se conservan backups para
diagnóstico siguiendo la skill de recuperación, sin limpieza automática.
Repetir una publicación idéntica usa un recibo nuevo y conserva bytes; para
recuperar el producto se apunta a la edición completa anterior, tras diagnóstico.

### Resolución reproducible del digest

La primera diferencia entre el entorno host y uv.lock era únicamente
`schema.columns[7].dtype`, control `in_epi_coverage`: `bool[pyarrow]` frente a
`boolean`. PyArrow 25.0.1 instalado en el host hace que pandas `string_storage=auto`
produzca booleanos Arrow en comparaciones. El lock no incluye PyArrow. Todas
las filas y valores coincidían. Forzar `string_storage=python` en el host, sin
otro cambio, restaura exactamente ambos hashes esperados. El productor fija
ahora `.astype("boolean")`: funciona también con Arrow sin alterar valores.
Main limpio y rama con lock coinciden; normal/-O pasan sin modificar expectativas
ni evidencia histórica. [Diagnóstico agregado](../evidence/risk-2025/20261114-recovery.json).

El E2E completo usa el API venv propio. Prepararlo desde la raíz antes de la
suite: `uv venv app/api/.venv --python 3.12` y
`uv pip install --python app/api/.venv -r app/api/requirements-dev.txt`; instalar
Bun con `bun install --frozen-lockfile --cwd app/dashboard`. CI ejecuta estas
mismas preparaciones, sin añadir dependencias de producto al lock científico.
